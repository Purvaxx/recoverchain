A complete scan of the `dataset/` directory was performed. The dataset lab successfully profiled major candidate datasets. Huge files (>50MB, e.g., `billing.csv` at ~274MB with 4.4M rows) were streamed via chunked processing to prevent memory overflows.

*   `billing.csv`: 4,424,748 rows, 10 cols. (Subscription billing histories)

## 2. CLASSIFICATION & TRAINING PRIORITY (VERIFIED)

*   **TIER 1 — PRIMARY TRAINING CANDIDATE (Directly Useful)**
    *   `WA_Fn-UseC_-Accounts-Receivable.csv`: Represents true merchant Accounts Receivable (AR). Exactly matches our domain.
    *   `billing.csv`: Massive dataset of subscription billing, late fees, and ultimate payment statuses. Excellent for baseline recovery probability.
*   **TIER 2 — SUPPORTING TRAINING DATA**
    *   `fraud_data_20251225_004640.csv`: Useful for root-cause diagnosis (fraud vs. organic failure) due to `error_code` and `fraud_reasons` columns.
    *   `Financial_Ecosystem_Dataset_T1_5k_.csv`: Deep feature-set for assessing counterparty risk and delinquency.
*   **TIER 3 — FEATURE ENGINEERING / REFERENCE**
    *   `ecommerce_customer_churn_dataset.csv`: Helps model the downstream effect of payment friction (churn).
    *   `upi_transactions_2024.csv`: Useful if we build a UPI-specific integration, otherwise reference-only.
*   **TIER 4 — DO NOT USE FOR TRAINING (Rejected)**
    *   `audit_trail.csv`: Rejected. Contains simulated output from our own deterministic RecoverChain engine. Using this would create a feedback loop of artificial data.
    *   `AR_AP_Analytics_Dashboard_FINAL.xlsx`: Rejected. Pre-aggregated dashboard reporting, not row-level events.

## 4. POTENTIAL TARGETS & LEAKAGE RISKS (VERIFIED)

**Candidate Targets Found:**
*   **Dataset:** `WA_Fn-UseC_-Accounts-Receivable.csv`
    *   **Target:** `SettledDate`, `DaysToSettle`
    *   **Leakage Risk:** HIGH. These fields are populated *only after* the invoice is closed. They must be strictly stripped from the input feature vector at Day 0 (Event Ingestion).
*   **Dataset:** `billing.csv`
    *   **Target:** `payment_status`, `days_to_payment`
    *   **Leakage Risk:** HIGH. `payment_status` indicates the eventual resolution.
*   **Dataset:** `fraud_data...csv`
    *   **Target:** `status` (Failed/Success), `is_suspicious`
    *   **Leakage Risk:** LOW for Risk Assessment, as these are provided synchronously by the payment gateway at the time of failure.

**Temporal Split Strategy:** 
We must use chronological splits (e.g., train on 2023, test on 2024) rather than random shuffles. `InvoiceDate` (WA_Fn) and `year_month` (billing) fully support safe temporal validation without time-travel leakage.

## 5. POSSIBLE DATASET JOINS (UNVERIFIED / HIGH RISK)

*   **Identified:** `retail_data.csv` and `ecommerce_customer_churn_dataset.csv` both contain customer behavioral data, but there is no explicitly shared `Customer_ID` namespace verified between them.
*   **Verdict:** **DO NOT JOIN.** Assuming identifiers from separate Kaggle/open datasets map to the same real-world entities will destroy dataset integrity. We will treat them as isolated distributions.

## 6. MISSING INFORMATION (VERIFIED)

Comparing our available datasets to the theoretical RecoverChain pipeline, we are explicitly missing data for **Action-Conditional Outcomes**:
*   `Candidate Action Attempted` (e.g., "Sent SMS", "Offered 10% Discount", "Triggered Stripe Retry")
*   `Action Timestamp`
*   `Action Cost`

**Conclusion:** We do not have sufficient historical supervised labels to train the `Action Recommendation` engine end-to-end. Any action recommendation must remain **heuristic/deterministic (PolicyEngine)** or rely on reinforcement/LLM-based contextual ranking rather than supervised offline training.

## 7. RECOMMENDED FIRST ML TASK (VERIFIED)

**RECOMMENDATION:** **Recovery Probability Prediction (Baseline)**

**Reasoning:** 
We have massive, high-quality, explicitly labeled datasets (`billing.csv` and `WA_Fn`) containing the organic outcome of payment failures (`SettledDate`, `DaysToSettle`, `payment_status`). 

We should train a supervised model to predict **P(Recovery | Case Evidence)** assuming *baseline standard collections*. This directly empowers the existing deterministic Policy Engine by accurately prioritizing high-risk cases (low organic recovery probability) for immediate escalation or aggressive actions, without requiring us to manufacture fake "Action" labels.
