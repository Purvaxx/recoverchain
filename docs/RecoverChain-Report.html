RecoverChain

Abstract

Abstract

Businesses that bill customers — subscriptions, invoices, marketplaces, checkouts — lose a persistent slice of revenue not because customers refuse to pay, but because a payment fails, an invoice slips past its due date, or a checkout is abandoned. This involuntary leakage is usually chased with blind retry schedules and generic reminder emails that treat every failure alike.

RecoverChain reframes recovery as a decisioning problem. Failure events are correlated into cases, and every case is driven through one fixed, auditable lifecycle: assess risk → diagnose the root cause → predict the odds of recovery → recommend the next-best action and its expected recoverable value → clear a policy and safety gate → execute in a sandbox → verify the outcome against a settlement source → write an audit record. Each stage is a small deterministic rules engine that produces an explanation a human can read.

A second subsystem, the Dataset Lab, lets a user upload an arbitrary CSV, Parquet, or Excel file; it semantically maps columns to canonical fields, runs leakage detection and a minimum-information contract, trains a per-dataset model, and replays the rows through the pipeline to produce real cases. Crucially, every model is shadow-only: its probability feeds ranking and prioritisation but is architecturally barred from authorising an action — the deterministic policy engine is the sole authority, and prediction always falls back to a deterministic baseline rather than a silent zero.

The system is delivered as a FastAPI backend (clean domain / application / infrastructure layering, SQLAlchemy + Alembic, Decimal money) and a React single-page frontend presenting a ten-step guided workflow plus a gated aggregate report. It runs fully offline with no external service calls. The implementation is validated by 216 automated backend tests (88% line coverage), an end-to-end walk-through of the ten-step workflow in a browser, and a hardening pass that added authentication on every mutating route, a request rate limiter, CORS correctness, container and CI security, and a lint / type-check / coverage gate.

Section 1

Introduction

1.1 General

Any organisation that charges customers on a recurring or deferred basis carries a structural revenue leak. A card expires between billing cycles; a bank declines a debit for insufficient funds; a network timeout drops a transaction; an invoice with net-30 terms is simply forgotten; a shopper fills a cart and closes the tab. None of these are a decision not to pay — industry practitioners call this involuntary churn, as distinct from voluntary cancellation. Left alone, a meaningful fraction of it never converts back into collected cash.

The established response is dunning: a scheduled sequence of automated payment retries and reminder messages. Payment processors ship retry logic (“smart” or “intelligent” retries) that pick retry times statistically; standalone dunning tools send escalating email/SMS sequences; larger finance teams run in-house scripts and manual collections queues. These approaches share a blind spot: they act on a schedule, not on a diagnosis. A retry fired at a card that expired is wasted. A payment-link email sent to a customer whose bank is rejecting the mandate solves nothing. And when teams do reach for machine learning to prioritise, the model frequently ends up in the loop — deciding what runs — which in a financial-actions context is difficult to audit, explain, or safely roll back.

RecoverChain is built around a different premise: the decision of whether and how to act on a failed payment should be made by a transparent, deterministic rulebook, with every stage of reasoning recorded, and with statistical models contributing only prioritisation signal that can never, by construction, trigger an action.

1.2 Problem Statement

Design and build a system that, given a stream (or a bulk file) of revenue-failure events, will for each affected account:

  1. Correlate related events into a single case so that a retry of the same invoice is one case, not two.
  2. Produce an explainable assessment at every stage — risk level, likely root cause, recovery probability, recommended action, and expected recoverable value — each with the signals that produced it.
  3. Pass the recommended action through a policy and safety gate that enforces retry caps, cooldowns, contact-frequency limits, an automated-amount ceiling, consent, and hard stop rules, using the account’s real prior-attempt history.
  4. Execute only what the gate permits, in a simulated environment (no live money movement), with idempotency so a replay produces the same record.
  5. Verify the true outcome independently against a settlement source rather than assuming an executed action succeeded.
  6. Accept arbitrary tabular datasets, understand their columns, check them for target leakage and sufficiency, train a model on them, and score real rows — without that model ever gaining authority over an action.
  7. Run fully offline, persist a complete audit trail, and be safe to demonstrate and hand over.

Section 2

Literature Review

RecoverChain draws on four strands of prior work and practice: dunning / involuntary-churn management, payment-failure prediction, safe deployment patterns for machine learning, and human-in-the-loop decision support.

Involuntary churn and dunning management

The subscription-economy literature and vendor practice (recovery and billing platforms, processor retry engines) establish involuntary churn as a first-class, recoverable revenue category and dunning — timed retries plus escalating customer messaging — as the standard mitigation. The consistent finding is that timing and message sequencing matter, and that naive fixed schedules leave money uncollected. RecoverChain accepts the dunning primitives (retry, reminder, payment-link, payment-method update, escalation) but subordinates them to a per-case diagnosis rather than a global schedule.

Payment-failure and churn prediction

Supervised models — gradient-boosted trees prominent among them — are widely used to estimate the probability that a given charge will fail or that a subscriber will lapse, using billing history, tenure, payment-method attributes, and prior-failure counts. Two recurring methodological hazards are emphasised in this literature: target leakage (post-outcome columns such as a settlement date or final status leaking the answer into the features) and improper validation (random splits on time-ordered data inflating scores). RecoverChain’s Dataset Lab operationalises both defences: an explicit leakage detector that quarantines post-outcome columns, and a chronological train/validation/test split with a flagged stratified fallback.

Safe ML deployment — shadow mode

Work on the operational risks of production ML (notably the “hidden technical debt” framing from Sculley et al., 2015) motivates shadow deployment: running a model against live traffic while its outputs are logged and compared but never acted on. RecoverChain adopts shadow mode not as a transient rollout phase but as a permanent architectural boundary — the predictor cannot be promoted into the decision path without changing the type signature of the policy engine, and the model card states this explicitly.

Rules engines vs. learned policies; human-in-the-loop

Decision-support research contrasts transparent rule systems (auditable, explainable, brittle to novelty) with learned policies (adaptive, opaque). For regulated financial actions the auditability requirement dominates. RecoverChain uses deterministic rules for every decision, reserves ML for ranking, and inserts an explicit human-escalation state (ESCALATE / human-review endpoint) for cases above the automated-amount ceiling or flagged by a stop rule — a conventional human-in-the-loop checkpoint.

Positioning

Where prior systems either schedule blindly or let a model decide, RecoverChain contributes a concrete architecture in which a diagnosis-driven deterministic pipeline makes every decision, a ledger-backed policy gate enforces safety against real history, and a permanently shadowed model supplies only prioritisation — all runnable offline with a full audit trail.

Section 3

Existing System

3.1 Traditional System

In current practice, recovery of failed revenue is handled by some combination of:

  • Processor-native retries. The payment gateway re-attempts a failed charge on a built-in cadence (fixed intervals, or a statistically chosen “smart” time). Configuration is coarse — typically a retry count and window — and the retry has no view of why the charge failed.
  • Standalone dunning / recovery tools. A SaaS product watches for failed invoices and sends a pre-authored email/SMS sequence (“your payment failed” → “reminder” → “final notice”), optionally with a hosted card-update page. Sequences are the same for every customer and every failure reason.
  • In-house scripts. A finance or growth team writes cron jobs that query the billing database and fire retries or emails against hand-tuned thresholds. Logic accumulates as special cases; there is rarely an audit trail or a safety layer.
  • Manual collections. For high-value B2B invoices, a human works a queue: calls, emails, escalations. Effective but unscalable, and the reasoning lives in the collector’s head.
  • Bolt-on ML scoring. Some teams add a churn/failure model to prioritise the queue. When the model’s score is wired directly into “who gets retried / dunned”, it becomes an unaudited decision-maker.

3.3 Limitations of the Existing System

  • Schedule, not diagnosis. Retries and reminders fire on a calendar regardless of the failure reason, so effort is spent where it cannot work (expired card, rejected mandate, disputed invoice).
  • One cadence for everyone. A ₹49 mobile top-up and a ₹9,800 B2B invoice get the same treatment.
  • No explanation. When a customer is retried or emailed, there is no recorded reason, confidence, or expected value — nothing to review or appeal.
  • Weak or absent safety layer. Contact-frequency and retry caps, cooldowns, consent, and hard stops are partial, per-tool, or written in a policy document rather than enforced in code against real history.
  • “Send equals recovered.” Success is inferred from having sent a message or fired a retry, not from confirmed settlement.
  • Unaudited ML. Where a model is used, its score often silently drives who gets actioned, with no boundary preventing it and no record of its influence.
  • Rigid data assumptions. Each tool expects its own schema; feeding in a novel billing export or testing a hypothesis on historical data is not supported.
Section 4

Proposed System

RecoverChain is a two-part system: a decisioning core that runs every case through one auditable lifecycle, and a Dataset Lab that turns an arbitrary tabular file into scored cases — presented through a ten-step guided workflow and a gated report.

4.1 Feature Overview

Decisioning core

  • Event ingestion & correlation. Single (/events) or bulk (/events/batch) revenue-failure events, deduplicated by external_event_id and correlated into cases by reference_id.
  • Risk assessment. A bounded score (amount curve 1−e−amount/800 combined with retry / age / churn sub-scores per category) mapped to LOW / MEDIUM / HIGH / CRITICAL, with the contributing signals returned.
  • Root-cause diagnosis. Evidence from the linked events is matched to nine cause categories (INSUFFICIENT_FUNDS, PAYMENT_METHOD_INVALID, NETWORK_FAILURE, MANDATE_FAILURE, UNRESOLVED_DISPUTE, MISSED_COMMITMENT, PAYMENT_FRICTION, CONFLICTING_EVIDENCE, UNKNOWN) with a confidence and CONFIRMED / INFERRED / UNKNOWN status.
  • Recovery prediction. A probability from a per-dataset shadow model when one exists and passes the quality gate, otherwise from DeterministicBaselinePredictor — never a silent zero. Always labelled SHADOW_ONLY.
  • Action recommendation + ERV. Candidate actions are generated for the diagnosed cause, scored, and ranked; the top candidate carries an expected recoverable value (amount × probability factor).
  • Policy & safety gate. DeterministicPolicyEngine returns PERMITTED / WAIT / ESCALATE / DENIED after evaluating stop, consent, evidence, human-escalation, automated-amount, max-retries, retry-cooldown, and contact-frequency rules — counting real attempts from the ledger when a PolicyContext is supplied.
  • Sandboxed execution. AgentOrchestrator dispatches the permitted action to a specialist agent through MockExecutionAdapter; requires a fresh matching PERMITTED decision; idempotent via idempotency_keys; writes an execution_attempts ledger row.
  • Independent verification. VerificationEngine reconciles against a SANDBOX_SIMULATION settlement source; the actual recovered amount comes only from the RecoveryOutcome and is clamped to [0, amount].
  • Audit. Every state transition writes an audit_records row with from/to state and an evidence blob.
  • Observability. Read-only /system/* endpoints expose cases, events, models, executions, policy decisions, audit, and a CSV export.

Dataset Lab

  • Upload CSV / Parquet / XLSX / ZIP (size-capped, path-sanitised, auth-guarded).
  • Profiling & semantic mapping. Columns are profiled and mapped to canonical fields (ENTITY_ID, AMOUNT, TIMESTAMP, TARGET, …) with confidence; the pipeline pauses at MAPPING_REVIEW for user confirmation and validates overrides server-side.
  • Quality & leakage. A data-health score, completeness breakdown, dead-column check, and a leakage detector that quarantines post-outcome columns.
  • ML-readiness contract. Derives target, feature and excluded columns (identifier / constant / post-outcome / high-cardinality, each with a reason), the temporal split strategy, and class balance; blocks datasets failing the minimum-information contract.
  • Per-dataset training. An sklearn Pipeline (text→numeric/epoch coercion, impute, scale, one-hot, LogReg + XGBoost candidates, calibration) with a chronological split and a ROC-AUC ≥ 0.55 quality gate; failing models are stored REJECTED_LOW_QUALITY.
  • Replay. generate-cases reads rows, auto-trains a model, and runs each row through the full pipeline — producing real, inspectable cases with honest accepted/skipped counters.
  • Registry hygiene. Dataset pruning that also sweeps orphaned model artifacts; strict dataset↔model isolation by dataset_id.

4.3 Benefits over Existing Solutions

  • Effort follows the diagnosis. A case caused by an expired card is routed to a card-update request, not a doomed retry; a disputed invoice is escalated, not reminded.
  • Every output is defensible. Risk, cause, probability, action, and value each ship with their signals and confidence; the policy verdict is rule-by-rule; all of it is in the audit table.
  • Safety is enforced, not documented. Retry caps, cooldowns, contact limits, an amount ceiling, consent, and stop rules are code, evaluated against the real attempt ledger.
  • Outcomes are measured, not assumed. Recovered amounts come only from an independent settlement check.
  • ML cannot misfire. The model is structurally unable to authorise an action; absence or low quality degrades gracefully to a deterministic baseline.
  • Any dataset, safely. The Dataset Lab makes historical experimentation a first-class feature, with leakage and sufficiency checks built in.
  • Runs anywhere, needs nothing. No CDN, no external API, Redis optional — demonstrable on a laptop with no network.
Section 5

Concept & Methodology

5.1 Guiding concepts

  • The case as the unit of work. Individual events are noisy and duplicative; the RecoveryCase aggregate is what carries state, accumulates the seven stage sub-objects, and is persisted and reasoned about.
  • One lifecycle, always the same order. There is exactly one path through the stages. This makes the system predictable, testable stage-by-stage, and auditable — the sequence of audit_records for a case is a complete, ordered story.
  • Determinism for decisions, statistics for priority. Anything that changes what the system does is a pure function of the case and explicit policy. Anything learned from data only changes the order in which humans or the queue see cases.
  • Shadow mode as a boundary, not a phase. The predictor returns shadow_mode_active: true and its value is never a parameter to policy evaluation. Promoting it would require changing a type signature — a deliberate, reviewable act.
  • Honesty in the UI. Every screen states whether a number is a rule output, a shadow-model estimate, or a simulation; execution and settlement are labelled SANDBOX_SIMULATION.
  • Offline-first. A hard constraint that shaped dependency choices (bundled fonts, no CDN, Redis optional, a hand-rolled StateGraph where a library needed a blocked native module).

5.2 Software methodology

  • Clean / layered architecture (DDD-influenced). domain/ is framework-free Pydantic models and the state machine; application/ is one engine per stage plus orchestration; infrastructure/ is ORM, repositories, adapters; api/ is thin FastAPI routers. Dependencies point inward only.
  • Test-first, invariant-driven. The safety invariants (ML shadow-only, execution simulated, policy is sole authority, financial clamping, dataset↔model isolation, migrations own the schema, auth on mutating routes) each have dedicated regression tests. The suite runs against an isolated throwaway SQLite database.
  • Iterative, phase-by-phase delivery. The project advanced through ~24 numbered build phases (architecture notes for phases 4–23 are kept under docs/history/) and 33 commits, each a self-contained, test-green increment — from “make the live case loop flow” through “ledger-backed policy”, “ML quality gate”, “offline”, the 10-step workflow redesign, real-data training, a performance fix, and the security/tooling hardening pass.
  • Reproducible ML. Training is a single scripted entry point (run_phase19_training.py); models are written to a registry with metadata (dataset id, split counts, metrics, status) and a model card documents intended use and limitations.
  • Environment-driven configuration. Behaviour (database URL, API key, CORS list, rate limits, upload cap, quality-gate thresholds, currency) is set by environment variables with safe offline defaults and a startup warning when insecure defaults are left in place.

Case state machine

CaseState has 21 members spanning the lifecycle: DETECTED → OPEN → ASSESSED → DIAGNOSING → RECOMMENDING → POLICY_EVALUATED, then a branch — APPROVED / DENIED / WAITING / ESCALATED / POLICY_REVIEW — then EXECUTION_PREPARING → EXECUTING → PENDING_VERIFICATION → VERIFYING, terminating in FULLY_RECOVERED / PARTIALLY_RECOVERED / CLOSED_NOT_RECOVERED or the out-of-band STOPPED. Every transition is written to audit_records with its true prior state.

6.6 Security architecture

  • Authentication. verify_api_key (X-API-Key header) guards every mutating route on both the case pipeline and the Dataset Lab; read-only GETs stay open for the dashboard. A startup check warns when the dev-default key or wildcard CORS is left in place.
  • Rate limiting. A stdlib sliding-window limiter (per key / per IP, default 120 req/min) as ASGI middleware; health and docs are exempt.
  • CORS. Wildcard origin and credentialed requests are mutually exclusive by spec — the app enables credentials only when an explicit allow-list is configured.
  • Uploads. Size-capped (MAX_UPLOAD_BYTES, 512 MiB default), extension-checked, filename path-sanitised, dataset-scoped storage names.
  • Container. Non-root user, health-check, migrations must succeed before serving. Compose requires explicit secrets rather than shipping defaults.
  • Frontend. The API key is build-time config (VITE_API_KEY), not a source constant; nginx sets CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, and gzip.
Section 7

Implementation

7.1 Stage engines (application/)

risk_detector

Computes a bounded amount score 1−e−amount/800 and combines it with a category-specific sub-score — retry count for failed payments/subscriptions, churn risk for checkout abandonment, age-in-hours for overdue invoices and broken promises — then maps the blended 0–1 score to LOW <0.3, MEDIUM <0.6, HIGH <0.85, CRITICAL, returning every signal used.

diagnosis_engine

Deterministic evidence matching from linked-event payloads to nine RootCauseCategory values, emitting a confidence and a CONFIRMED / INFERRED / UNKNOWN status plus supporting signal references. Receivables vocabulary (net_terms_pending, dispute, bank_rejected…) maps onto the shared cause set.

recovery_predictor / _ml

DeterministicBaselinePredictor gives a rules-based probability from cause and risk. MLPaymentFailurePredictor loads only a model whose metadata dataset_id matches exactly and whose status is not REJECTED_LOW_QUALITY; recovery probability = 1 − failure_risk. Both stamp SHADOW_ONLY.

action_evaluator

Generates candidate ActionTypes appropriate to the diagnosed cause and category, scores and ranks them, and attaches an expected recoverable value to the top candidate (amount × probability factor). Returns RECOMMENDED or INSUFFICIENT_EVIDENCE.

policy_engine

DeterministicPolicyEngine.evaluate(case, context) runs, in order: StopRule, ConsentCheck, EvidenceCheck, HumanEscalationAction, FinancialAutomatedLimit (₹5,000 default ceiling), PaymentMaxRetries (3), PaymentRetryCooldown (24 h), CommunicationMaxMessages (2 / 24 h). With a PolicyContext the retry/cooldown/contact counts come from the real ledger; without one it falls back to a linked-events proxy for unit tests. Result: PERMITTED / WAIT / ESCALATE / DENIED with per-rule detail.

agents / verification_engine

AgentOrchestrator.execute requires a persisted, fresh, matching PERMITTED decision and a capable specialist agent, dispatches through MockExecutionAdapter, and (given a repo) writes the idempotency key + ledger row. VerificationEngine.reconcile checks the SANDBOX_SIMULATION settlement source, sets the outcome status, and clamps the recovered amount to [0, amount].

case_pipeline.py’s CasePipelineService runs assess → diagnose → predict → recommend → policy in one call and is the shared path for /events/batch, /cases/{id}/advance, and generate-cases.

7.2 Dataset Lab (application/)

  • dataset_lab.py — registry service: import, list, prune; file storage under dataset-scoped names.
  • dataset_intelligence.py — SemanticMapper normalises column names, inspects values, and scores each column against canonical fields with HIGH / MEDIUM / LOW confidence; ambiguous single-use fields (AMOUNT, TARGET, TIMESTAMP…) are downgraded and flagged for user confirmation. DatasetValidator runs leakage detection and dataset classification (ANALYSIS_READY … INSUFFICIENT).
  • ml_readiness.py — derives target, feature columns, excluded columns with reasons, temporal-split strategy, and class balance; enforces the minimum-information contract.
  • ml_training.py — the training pipeline (below).

ML training pipeline

  1. Format-agnostic read — _read_any() branches on extension (Parquet / Excel / CSV).
  2. _coerce_frame step — turns number-like text ("1,200", "₹ 45") into floats and date-like text into epoch-day floats, at fit and predict time, so a messy real CSV transforms identically when served.
  3. Preprocessing — impute + scale numerics; one-hot categoricals with handle_unknown="ignore".
  4. Candidates — LogisticRegression and XGBClassifier, probability-calibrated on the validation fold (skipped and folded back into train when that fold is tiny or single-class).
  5. Split — chronological on the real date column; stratified fallback (flagged in metadata) when there is no usable temporal column.
  6. Quality gate — ROC-AUC ≥ ML_MIN_ROC_AUC (0.55) and rows ≥ ML_MIN_TEST_ROWS; an adaptive mode lowers the row floor for small real datasets. Failing models are written REJECTED_LOW_QUALITY and are never loaded.
  7. Registry — {model.joblib, metadata.json} keyed by dataset id, with split counts, metrics, and status.

7.3 Infrastructure

  • repositories.py — SqlAlchemyCaseRepository maps ORM ↔ domain, and provides record_execution_attempt and get_policy_context (which builds a PolicyContext from the execution_attempts ledger). Commits per use-case.
  • orm.py / dataset_orm.py — the seven tables; lifecycle sub-objects as JSON columns; timezone-aware timestamps.
  • adapters.py — MockExecutionAdapter and the settlement source; the only “external world” and both simulated.
  • langgraph_orchestrator.py — a hand-rolled StateGraph used only by the evaluation harness, because the real library needs a native module blocked in the target environment. Kept deliberately dependency-free.

7.4 API layer

Thin FastAPI routers. main.py carries the case-pipeline endpoints, batch ingest, advance/stop, a request-id + timing middleware, and the dashboard aggregation. dataset_router.py and system_router.py carry the Dataset Lab and read-only observability. auth.py and security.py hold the API-key dependency, the rate limiter, the startup config check, and the upload-size constant.

8.4 Machine-learning behaviour

  • A ~140-row engineered dataset auto-trains an XGBoost model (ROC-AUC ≈ 1.0 on its held-out fold) that then scores its cases SHADOW_ONLY.
  • Noisier small datasets correctly fail the 0.55 gate, are stored REJECTED_LOW_QUALITY, and the pipeline serves the DeterministicBaselinePredictor instead — never a silent 0.0.
  • In neither case does any probability enter a PolicyDecision; a dedicated regression test asserts the boundary.

8.5 Performance

An early defect made Step 06 appear to hang: predict_recovery_for_case() rebuilt a full sklearn+XGBoost predictor (scanning a ~400-file registry, joblib.load each call) once per row. The fix threads an optional pre-built predictor through the pipeline so generate-cases constructs it once.

8.6 Discussion

What works. The deterministic pipeline is genuinely explainable end to end — a case’s audit trail reconstructs every decision. The policy gate behaves correctly against real ledger history (the ₹15,000 case escalated exactly as configured). The shadow-only boundary held under test and in the live run. The Dataset Lab turns an arbitrary CSV into inspectable cases with leakage and sufficiency checks that actually fire.

Honest limitations. Execution and settlement are simulated — there is no live payment or communications adapter. The domain is still partly JSON-blob rather than fully relational, so cross-case querying is limited. Correlation needs a shared reference_id; there is no entity resolution across files yet. The dashboard aggregates in application code rather than SQL. The frontend has no automated tests. There is no multi-tenancy. The reference model’s training data provenance is unverified (documented in the model card). These are scoped in Section 10.

Section 9

Conclusion

RecoverChain demonstrates that failed-revenue recovery can be treated as a transparent decisioning problem rather than a blind schedule. Each failure becomes a case; each case runs one fixed, auditable lifecycle of small deterministic engines; a ledger-backed policy gate is the sole authority over whether an action runs; execution is sandboxed and idempotent; and the outcome is verified independently rather than assumed. Machine learning is present and useful for prioritisation, but is architecturally prevented from ever deciding — and degrades cleanly to a deterministic baseline when it is absent or weak.

The Dataset Lab extends the same discipline to arbitrary data: any tabular file can be mapped, checked for leakage and sufficiency, used to train a per-dataset model, and replayed into real cases — still without that model gaining authority.

The system is validated by 216 passing tests at 88% coverage, a clean end-to-end browser walk-through, and a hardening pass that makes it safe to deploy and demonstrate. It runs entirely offline. Within its deliberately simulated execution boundary, RecoverChain is a complete, coherent, and defensible implementation of diagnosis-driven revenue recovery.
